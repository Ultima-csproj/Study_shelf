# Работа над «Учебной полкой»

## Документация

По просьбе пользователя все значимые решения и изменения поведения записывать в `.codex/docs/*.md`.

- Перед работой прочитать `.codex/docs/README.md` и `.codex/docs/project-context.md`.
- Обновлять тематические документы при изменении соответствующего решения.
- После реализации дополнять `.codex/docs/changes.md`: цель, файлы, фактически выполненные проверки и ограничения.
- Сохранять утверждённый визуальный стиль и существующий рабочий код. Не начинать новый дизайн-цикл без запроса.

## Читаемость TypeScript/React

- Один statement на строку, отдельные объявления `const`.
- `if/else` с блоками; не уплотнять код ради краткости.
- Длинные ternary expressions переносить, сложные условия заменять читаемыми блоками.
- Длинные выражения JSX выносить в локальные переменные, props писать развёрнуто.
- Предпочитать простые решения с понятной точкой будущего подключения Axum API.

## Инспекция

Использовать `git ls-files`, `rg --files`, `rg`, ограниченные чтения через `System.IO`. Не читать весь проект без необходимости и не использовать большие рекурсивные PowerShell pipelines. Обычно не более пяти исходных файлов за команду.

## Структура фронтенда

- Группировать файлы по назначению и предметной области: редактор материала, история редакций, управление доступом, список автора — разные модули, а не одна плоская папка.
- Компонент и его собственный CSS module хранить рядом. Общие стили допустимы для явно общих элементов; не собирать оформление разных экранов в один большой stylesheet.
- Компоненты из `components/` не должны импортировать код или стили из `pages/`. Страница собирает компоненты; зависимости не должны идти в обратную сторону.
- Крупные формы и панели разделять по ответственности: поля, участники, действия, локальное состояние/валидация. Не дробить маленькие файлы без практической пользы.
- API, модели, hooks, компоненты и страницы разделять по ролям. Не смешивать запросы, побочные эффекты и большую разметку в одном файле, если их можно отделить понятными модулями.
- При расширении раздела сначала проверить существующую структуру и использовать подходящую папку. Не складывать новые несвязанные компоненты в ближайшую папку только ради удобства.
- При переносах обновлять все импорты, сохранять существующие изменения и поведение, выполнять сборку/lint. Значимые изменения структуры фиксировать в `.codex/docs/`.
